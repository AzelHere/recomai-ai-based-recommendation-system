# Recom AI measured performance

Two local trials compared the baseline and reviewed application against 2,365 resources in fresh isolated MySQL databases. Hardware allocation: Docker Desktop x86_64, 14 logical CPUs and 8,032,411,648 bytes (7.48 GiB) shared Docker memory; MySQL 8.4.11. Existing unrelated workloads remained running. These are short local workflow measurements, not a sustained capacity or production benchmark.

At each 10, 25, 50 and 100 concurrent generated actors, every actor executes eight sequential operations: catalog page, Java search, article/provider/topic filtering, recommendation generation, detail, saved list, three-step journey creation and progress. Five warm-ups per operation precede measurement. Requests have 30-second deadlines. Stop conditions include over 5% errors, a phase over 60 seconds, target memory over 80%, aggregate Docker memory over 85%, or over 120 schema connections. The larger 250/500 levels were not run on this shared 7.48-GiB allocation.

All measured levels in both trials completed without request errors. The [endpoint CSV](performance.csv) gives nearest-rank p50/p95/p99, means, response bytes and sample sizes for the complete second trial. Raw first/second trial JSON in the evidence ZIP includes phase throughput; the second trial additionally records per-phase CPU/memory end-samples and schema statement count/duration deltas. First-trial resource samples cover the last phase only. Resource samples are not peaks; query aggregates include operator probes and cannot establish per-endpoint query plans.

At 100 actors, trial-one phase durations were 3,159.5 ms before and 3,037.6 ms after; trial two was 3,111.9 ms before and 3,746.5 ms after. Variation overlaps and the second run is slower. No general throughput/latency improvement is claimed. Tests are closed-loop, one workflow per actor, with a synthetic fixture history; they do not model real traffic distributions or long-duration saturation.

One concrete payload problem was fixed: reloading a single administrator draft fetched the entire catalog. The measured response changed from 2,582,289 bytes to 615 bytes for one record, a 99.98% reduction for that operation. The route enforces administrator authorization, supports paused records and retains revision conflict handling. The frontend also checks workspace identity before applying a delayed reload. The legacy full-list route remains compatible but is unsuitable for single-record reloads.

No speculative database indexes or applied migration changes were made. Existing bounded paging and ownership/revision indexes are retained. Leading-wildcard substring predicates and expression sorts cannot be made selectively indexed merely by adding a conventional index. The evidence does not justify a schema rewrite. Larger-catalog query plans, selective search and sustained tests on dedicated hardware remain follow-up work.

Reproduce `QUALITY_IMAGE=<image> node scripts/technical-measure.mjs before` or `after`. The script imports licensed metadata and creates explicit synthetic accounts only inside its generated `recomai_quality_*` database. It has no option to load-test the private development database. Do not interpret stack-ready timing as a clean image-download/build time.
