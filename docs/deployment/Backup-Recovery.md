# Backup and restore

The automated exercise is `node scripts/phase4-backup-restore.mjs <isolated E2E project>`. It refuses project names outside `recomai-e2e-*`, checks the source database prefix, uses consistent `mysqldump --single-transaction --hex-blob --no-tablespaces --set-gtid-purged=OFF`, and restores into a newly generated `recomai_restore_*` database. It first restores a consistent live-fixture dump into a new quiescent snapshot database. It then backs up that immutable snapshot, restores a separate new database and compares sorted null-aware binary encodings and complete row SHA256 values/counts for every table. Concurrent browser writes cannot invalidate the comparison source. It never restores over the source. The test uses generated accounts only. Dump contents stay in memory, including any fixture credential hashes, and are never delivered. Both isolated databases remain in the retained test volume.

For an operator backup of valuable data, use a separate approved destination with restricted filesystem permissions, encryption and an explicit retention schedule. Supply credentials through the operator's secret manager rather than command-line arguments. Capture the source MySQL version, schema version and timestamp. Use a consistent logical dump with routines/triggers/events when those are present. Do not perform a backup during schema migrations. Transfer the encrypted backup to a separate failure domain; verify its checksum there. Backups include personal data and credential hashes and must not enter Git, this audit ZIP, source images or public hosting.

Restore first into a separate MySQL instance of the compatible version with a new empty database and restricted access. Validate Flyway checksums, table counts, foreign keys and sampled application login, preferences, provenance, Saved, collections, activity, progress, journeys and settings. Test SMTP with a capture sink, not real recipients. Compare exact row fingerprints when a quiescent snapshot is available; otherwise compare against the backup snapshot rather than the moving source. Only a separately authorized recovery procedure should switch application traffic. No valuable-data restore or production switchover was performed in Phase 4.

The checked-in script is a recovery test, not an unattended production backup system. Scheduled encrypted backups, retention monitoring and a documented recovery-time/recovery-point objective remain deployment responsibilities.


## Phase 5 review
The prior isolated 30-table restore is retained as evidence and the final browser regression reuses the isolated verification. No recovery operation runs against the valuable database. MySQL logical dump uses single-transaction consistency with no concurrent DDL; the moving fixture is first restored to a quiescent snapshot, then dumped/restored and every sorted null-aware binary-safe table row hash/count compared. Required permissions depend on flags and schema objects; use the restricted operator credential, avoid password arguments, confirm SHOW VIEW/TRIGGER/EVENT privileges only if those objects are included. Never treat raw volume snapshots as a consistent MySQL logical backup. Set documented RPO/RTO, retention, encryption, off-host copies, access logs and periodic isolated restore rehearsal before production. A private backup is never included in Git or submission ZIPs.
